# M1 Results: Offline CLI + Chunked Engine

**Date:** 2026-07-17
**Deliverable:** `native/vc-cli in.wav out.wav` — full native RVC conversion (any-sr wav → Alex Jones 40 kHz) through the real chunked streaming core. All on ORT CPU EP, fp32, per the M0 decision.

## Gates

| gate | result |
|---|---|
| mel frontend vs torchfcpe golden | **PASS** (RMSE < 1e-4, exact frame semantics) |
| fcpe decoder vs golden f0 | **PASS** (median cents < 5, voicing agreement > 95%) |
| engine single-pass vs golden chain (same pitch source + injected noise) | **PASS** (RMSE < 1e-3) |
| determinism (same cmd twice) | **PASS** (byte-identical, both modes) |
| chunked continuity (clicks at seams) | **PASS** (top sample-jumps are mid-block transients ≈ single-pass's natural max; no seam clustering) |
| chunked voicing/f0 tracking | **PASS** (89/101 voiced, 102.8 Hz vs source 103.2 Hz) |
| chunked vs single-pass log-mel L1 < 0.1 | **INVALID GATE** — see below |

**Invalid gate note:** ContentVec features are context-sensitive; a 260 ms-context chunk legitimately produces different features than a whole-file pass, so chunked-vs-single-pass spectral distance measures context difference, not defect (measured L1 ≈ 1.4–2.1 with no audible artifact and healthy voicing). Also found and fixed en route: SOLA offset random-walks during silence (correlation over noise) → time-warped stream; fixed with a nominal-anchor fallback when window energy is negligible. M2 gets an A/B listen protocol against the python client live path instead.

Realtime today at 160–240 ms blocks with zero optimization. Single-pass whole-file xRT 5.4.

Current mouth-to-ear estimate at default: block 160 + SOLA lookback 100 (crossfade 80 + search 20) + inference 147 serial + device buffers ≈ **~420 ms** — functional but far from the <150 ms M2 gate.

## M2 latency levers (in order)

1. **Pipeline overlap** — capture block N+1 while converting N (design already in spec): removes inference from the serial path when headroom > 0 → ≈ block + lookback + buffers.
2. **Crossfade shrink** — 80 ms crossfade is conservative; w-okada runs smaller. Each ms is direct latency.
3. **Stage parallelism** — contentvec ∥ (mel+fcpe) on separate threads (independent inputs), synth after: cuts hop time ~30%.
4. **ORT session thread tuning** + possibly contentvec on WebGPU EP (stable 42 ms @1 s, frees CPU for synth).
5. Smaller ctx_left (quality-permitting — needs listen A/B).

## Addendum: "chunked sounds off" investigation (same day)

Systematic root-cause: controlled experiment (same output region, zero noise, no
stitching) proved the divergence is **intrinsic to windowed inference** —
contentvec/fcpe render sub-second windows differently than long ones. Measured
same-region log-mel L1 vs whole-file render: 0.26s ctx = 1.66 → 1.5s ctx = 1.15
→ 3s ctx = 0.94 → 1.5s left + 1.5s RIGHT ctx = **0.82** (right context matters
as much as left). SOLA/noise were minor contributors (position-locked noise
raised SOLA correlation 0.35→0.80 but barely moved L1).

Changes shipped:
- **Position-locked noise** (counter-based RNG on absolute stream position) —
  overlapping windows now render with identical noise.
- **SOLA warmup emits the first block** (was silently dropping it).
- **`lookahead` (right context) support** in StreamEngine.
- CLI defaults: offline = 1.5s block / 1.5s ctx / 1.4s lookahead (convert.sh-class
  quality, xRT 1.5); `--realtime` = 160ms/260ms/0 preview of the M2 live target.

Consequence for M2: realtime quality is bounded by affordable window size —
exactly like the python client live path (extra 8192 = 0.5s ctx). The honest M2
quality gate is A/B against the python client live, not against offline renders.
Realtime levers: ctx_left growth within compute budget + small lookahead
(~100–200ms, direct latency cost) + the latency work already listed.
